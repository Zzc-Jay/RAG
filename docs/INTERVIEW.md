#### Q1：整体介绍一下你的 RAG 系统架构

**考察点**：是否有全局视野，能否清晰表达数据流。

**回答框架**：

"系统分四层：
- **接口层**：Streamlit UI 和 FastAPI REST API 双界面，JWT 认证统一拦截
- **业务逻辑层**：知识库 CRUD → 文档处理（加载→切分→嵌入）→ 检索（向量+BM25+RRF）→ 生成（带引用）
- **基础设施层**：嵌入缓存（SHA256内容寻址）、审计日志（append-only）、速率限制（滑动窗口）、API重试（指数退避）
- **存储层**：ChromaDB（向量）、BM25 pickle索引、SQLite（缓存+审计+用户DB）

一次问答请求经过 10 个步骤：输入校验 → 查询嵌入 → 向量/BM25双路检索 → RRF融合 → 可选改写/精排 → Prompt构建 → LLM流式生成 → 引用返回 → 审计记录 → Token统计"

---

#### Q2：为什么选 ChromaDB 而不是 FAISS 或 Milvus？

**考察点**：技术选型能力，是否做过对比分析。

**关键点**：
- FAISS 是纯向量计算库，不提供持久化、元数据过滤、增删改——这些都要自己写
- Milvus 功能完整但需要独立部署，对中小规模项目太重
- ChromaDB 嵌入式架构，pip install 即用，内置持久化和元数据过滤，API 简洁

"我选 ChromaDB 是因为它在'轻量'和'功能完整'之间取得了最好平衡。如果数据量超过百万级，我会迁移到 Milvus——但当前架构下切换成本很低，因为我在 embedder 模块中封装了 `_get_collection()`，外部调用方不感知底层实现。"

---

#### Q3：chunk_size=800、chunk_overlap=150 是怎么定的？

**考察点**：是否理解参数含义和权衡。

**关键点**：
- 800 字符 ≈ 400 tokens（中文），正好在 embedding 模型的最佳输入范围内
- overlap=150 保证跨 chunk 边界的上下文不丢失
- 不是拍脑袋——是通过观察文档自然段落边界和检索结果质量调出来的

"chunk_size 太小会导致语义碎片化，太大则稀释检索精度。800 字符是 embedding 模型推荐的输入范围（≤512 tokens），overlap=150 保留约 20% 的上下文重叠，避免关键信息恰好被 chunk 边界切断。DashScope text-embedding-v3 单次 API 调用上限是 10 条，所以我 BATCH_SIZE=10 也是跟 API 限制对齐的。"

### 第二部分：检索算法（核心技术深度）

---

#### Q4：为什么用 RRF 融合而不是直接加权求和？

**这是你最大的面试亮点。**

**考察点**：对检索融合算法的理解深度。

**关键点**：
- 向量相似度（0~1余弦距离）和 BM25 分数（开区间，可能 0~50）**量纲不同**
- 直接加权意味着一种检索天然主导，权重参数毫无意义
- RRF 只关心**排名**，与分值尺度无关

**标准回答**：

"向量检索返回的是余弦距离（0~1），BM25 返回的是基于词频-逆文档频率的开放分数（可能 0 到几十）。两者量纲完全不同，直接做加权加法就像把摄氏度和华氏度直接相加——就算设了权重参数也不可控。

RRF（Reciprocal Rank Fusion）的思路是：不看分数看排名。每个文档在各自检索路径中的排名才是有意义的信息。公式是：

```
score(d) = w_vector / (k + rank_vector) + w_bm25 / (k + rank_bm25)
```

k 是平滑参数（默认 60），作用是让排名靠后的文档分数不会断崖式下降。k=0 时只有第一名能得高分，k=60 时前 10 名分数差距较平缓。

权重用 1.0/0.0 可切换到'纯语义'或'纯关键词'模式，用 0.5/1.0 可实现'偏向关键词'。这是工业界（Elasticsearch 8.x+）采用的标准融合方法。"

---

#### Q5：BM25 是什么？比 TF-IDF 好在哪？

**考察点**：传统信息检索算法基础。

**关键点**：
- TF-IDF 的 TF 部分线性增长——一个词出现 100 次权重就是出现 1 次的 100 倍，不合理
- BM25 用非线性饱和函数：词频贡献趋近一个上限，不会无限增长
- BM25 还考虑了文档长度归一化

**标准回答**：

"BM25 是 TF-IDF 的改进版本，两个核心改进：
1. **词频饱和**：一个词出现了 5 次和 50 次，对相关性的贡献差异不大。BM25 用 `tf/(k1+tf)` 做非线性映射，词频趋近 1.0。TF-IDF 则是线性 `log(1+tf)`，高词频被过度放大。
2. **文档长度归一化**：长文档天然包含更多词，BM25 用 `1-b+b*dl/avgdl` 做惩罚，防止长文档仅因长度而在检索中占优势。

在我的项目中，BM25 + jieba 分词负责关键词匹配，特别适合搜代码变量名、专有名词、数字型号这类 embedding 可能捕获不好的查询。"

---

#### Q6：你的 embedding 模型输出多少维？对中文支持怎么样？

**考察点**：对 embedding 模型的理解。

**关键点**：
- DashScope text-embedding-v3 输出 1024 维
- 中英文混合场景表现好，阿里通义千问同系列模型
- 1024 维 × 4 字节(float32) = 4KB/条，实际存储成本很低

---

#### Q7：流式输出是怎么实现的？

**考察点**：对 SSE 协议的理解。

**关键点**：
- 用 SSE (Server-Sent Events) 不是 WebSocket——SSE 是单向流（服务端→客户端），更简单
- GET 端点 `/api/kb/{name}/query/stream`，响应 `Content-Type: text/event-stream`
- 每生成一个 token 就 `yield f"data: {json.dumps(token)}\n\n"`
- 结束标记 `data: [DONE]\n\n`

"我用 SSE 而不是 WebSocket 的理由：RAG 问答只需要服务端推送答案 token，客户端不需要同时发送数据。SSE 比 WebSocket 简单很多——原生 HTTP，自动重连，不需要握手升级协议。Streamlit 端用生成器迭代消费，FastAPI 端用 StreamingResponse 包装。"

### 第三部分：工程能力

---

#### Q8：系统瓶颈在哪？能抗多少 QPS？

**考察点**：性能分析能力。

**回答思路**：
1. **瓶颈 1：LLM API 延迟**。DashScope qwen-plus 生成 ~20 tokens/s，是最大延迟来源（3~10 秒/请求）
2. **瓶颈 2：Embedding API 调用**。单次 ~200ms，但嵌入缓存命中后直接跳过
3. **ChromaDB 不是瓶颈**——中小规模下向量检索 <10ms
4. **并发能力**：当前单进程同步模式约 2~5 QPS，FastAPI 用 async 可提升到 20+

"如果要提升吞吐，我会优先做三件事：① embedding 结果全部缓存，减少 API 调用；② 检索结果也做缓存（相同 query 短时间内复用）；③ 用 FastAPI 的 async endpoint 配合异步 HTTP 客户端，让 IO 等待期间可以处理其他请求。"

---

#### Q9：10 万条向量后查询性能如何？

**考察点**：了解 ChromaDB 底层实现。

**关键点**：
- ChromaDB 底层用 HNSW 图索引，10 万条的查询延迟约 5~20ms
- 配合元数据过滤可以进一步缩小搜索范围
- 真正出问题的是 brute-force 场景——但 ChromaDB 1.5+ 已默认启用 HNSW

"HNSW 图索引的查询复杂度是 O(log N)，10 万和 100 万的查询延迟差距很小。超过百万级后，考虑给 ChromaDB 加 metadata 分区（如按知识库/文档类型），每个分区的向量数量控制在万级。"

---

#### Q10：500 页 PDF 会出什么问题？

**考察点**：对边界情况的考虑。

**关键点**：
- 切分后可能产生 1000+ chunks，embedding API 调用次数 = 1000/10 = 100 次
- 每批 10 条的 API 限制下，串行处理需要 100 × 200ms = 20 秒
- 处理期间如果失败，已嵌入的数据已经 upsert 到 ChromaDB，需要回滚

"我当前的实现是分批嵌入，每 10 个文本块调用一次 API。500 页 PDF 可能产生 1000+ chunks，需要 100 次 API 调用，约 20 秒。两个风险需要处理：① API 调用失败时已有数据怎么回滚——我用了 upsert 而非 insert，失败后重新处理同一文件时旧数据会被覆盖；② 长时间处理时用户会以为卡住了——Streamlit 的 st.status 组件显示实时进度。"

---

#### Q11：怎么评估检索质量？

**考察点**：是否有质量评估意识。

**关键点**：
- 工业常用：MRR(Mean Reciprocal Rank)、nDCG、Recall@K
- 需要标注数据（query + 正确答案对应的文档片段）
- 先用少量标注做基线，后续通过用户反馈（点赞/踩）收集更多信号

### 第四部分：设计与反思

---

#### Q12：如果重新设计，会改什么？

**考察点**：有反思能力，不盲目自夸。

**可说的改进点**：

1. **异步化**：当前 embedder 和 generator 都是同步调用 API，IO 密集场景下用 asyncio + aiohttp 可以显著提升吞吐
2. **增量更新**：当前修改文档需要删了重传。应该设计成增量 upsert + 只重建变化的 chunk
3. **检索评估**：缺乏系统化的质量评估方法，只能人工判断检索效果
4. **文档更新检测**：用文件哈希检测文档是否有变化，只有变化时才重新处理

"这些都是我在面试过程中学到的——一个系统要在真实场景下用起来，还有很多边角要打磨。但我觉得项目在这个阶段已经完整展示了我的架构设计能力和工程实践水平。"
