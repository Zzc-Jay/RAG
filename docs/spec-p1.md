# Spec: P1 打磨阶段 — 从可用到好用

> 目标：补齐多轮对话、成本可见性、用户反馈等用户体验关键能力。

---

## Objective

在 P0 稳定性的基础上，增加多轮对话上下文、Token 用量统计、回答操作和用户反馈，让系统从「功能可用」升级为「体验好用」。

### 用户故事

1. **多轮对话** — 提问后可以追问，系统记住前面的上下文，不用每次重复背景信息
2. **成本可见** — 每次提问后能看到消耗了多少 token、大概多少钱
3. **回答可操作** — 可以一键复制回答、导出对话记录
4. **反馈闭环** — 对回答质量点赞/踩，不满意时知道哪出了问题

### Success Criteria

- [ ] 连续 3 轮追问，系统能正确理解上下文指代
- [ ] 每次回答下方显示 token 消耗（输入 + 输出）和估算费用
- [ ] 侧边栏显示 session 累计 token 用量
- [ ] 回答旁有一键复制按钮，复制成功有视觉反馈
- [ ] 可导出当前对话为 Markdown 文件
- [ ] 点赞/踩记录写入日志文件，含时间戳和对话上下文
- [ ] 对话历史仅保留最近 N 轮（可配置），超出自动截断

---

## P1-1: 多轮对话历史

### 现状问题

每次提问独立处理，无上下文记忆。用户问「它有什么优点？」时，系统不知道「它」指什么。

### 需求

| ID | 需求 | 优先级 |
|----|------|--------|
| H1 | 记录每轮问答（问题、回答、引用来源） | must |
| H2 | 生成新回答时将最近 N 轮历史注入 prompt | must |
| H3 | 支持追问和指代消解（至少覆盖代词「它」「这个」） | must |
| H4 | 对话轮数上限可配置（默认 5 轮） | must |
| H5 | 切换知识库时清空对话历史 | should |
| H6 | 「清空对话」按钮手动重置 | should |
| H7 | 对话历史超过 token 阈值时自动摘要压缩 | could |

### Prompt 设计变更

```
旧（单轮）:
  参考资料 + 问题 + 回答

新（多轮）:
  对话历史（最近 N 轮）+ 参考资料 + 当前问题 + 回答
```

## P1-2: Token 统计与成本可见

### 现状问题

无任何用量统计。开发者不知道每次调用消耗了多少 token，无法评估成本。

### 需求

| ID | 需求 | 优先级 |
|----|------|--------|
| C1 | 每次 embedding 记录输入 token 数 | must |
| C2 | 每次 generation 记录输入 + 输出 token 数 | must |
| C3 | 回答下方显示本次消耗（token 数 + 估算费用） | must |
| C4 | 侧边栏显示 session 累计统计 | must |
| C5 | 日志中记录每次 API 调用的 token 用量 | should |
| C6 | DashScope 未返回 usage 时优雅降级（显示「未知」） | must |

### 费用估算

DashScope 定价参考（2026 年）：
- qwen-plus: 输入 0.0008 元/1K tokens，输出 0.002 元/1K tokens
- text-embedding-v3: 0.0005 元/1K tokens

## P1-3: 回答操作

### 现状问题

回答只能看，不能复制、不能导出、不能分享。

### 需求

| ID | 需求 | 优先级 |
|----|------|--------|
| O1 | 回答旁「复制」按钮，点击复制全部回答文本 | must |
| O2 | 复制成功后显示「已复制」反馈 | should |
| O3 | 「导出对话」按钮，下载为 .md 文件 | should |
| O4 | 导出内容包含问题、回答、引用来源、时间戳 | should |

---

## P1-4: 用户反馈

### 现状问题

回答质量好坏无反馈机制，无法积累数据做检索优化。

### 需求

| ID | 需求 | 优先级 |
|----|------|--------|
| F1 | 每轮回答下方 👍/👎 按钮 | must |
| F2 | 点击后记录到 JSON 日志（含问题、回答、引用、时间） | must |
| F3 | 点击后有视觉确认（按钮变色） | should |
| F4 | 踩了之后可选填原因（如「不相关」「不准确」） | could |

---

## Out of Scope (P1 不包含)

| 项目 | 原因 |
|------|------|
| Query 改写/扩展 | 需要 LLM 调用改写查询，体量+复杂度升一级，放入 P2 |
| Reranking 模型 | 需要额外的 reranker 模型或 API，放入 P2 |
| 文档增量更新/版本管理 | 需要变更 ChromaDB 和 BM25 的更新策略，设计复杂 |
| REST API | 需要 FastAPI 重构整个服务层，放入 P2 |
| 用户认证 | 需要数据库 + session 管理，放入 P3 |
