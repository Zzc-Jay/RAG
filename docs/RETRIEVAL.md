# 混合检索与 RRF 融合 — 核心原理详解

这是本项目的**核心技术亮点**，也是面试中最能拉开差距的话题。

---

## 问题背景

### 为什么需要混合检索？

知识库检索有两种基本思路：

| 方式 | 原理 | 擅长 | 短板 |
|------|------|------|------|
| **向量检索**（Dense） | 文本→向量，算余弦距离 | 语义相似、"意思相近" | 专有名词、代码、数字 |
| **关键词检索**（Sparse） | 分词→词频统计，算相关性 | 精确匹配、专有名词 | 同义词、改写表达 |

**举例说明两种方式的行为差异**：

```
知识库中存在: "API_VERSION 常量定义为 3.0"

用户查询: "api version"
  → BM25: 直接命中 "API_VERSION"，得分很高 ✓
  → 向量: "api version"和"API_VERSION 常量定义为 3.0"语义不够接近，得分中等 △

用户查询: "如何设定接口的版本号"
  → BM25: "接口"、"版本号"匹配不到 "API_VERSION"，得分低 ✗
  → 向量: 语义理解"接口版本号"≈"API_VERSION"，得分高 ✓
```

**单一检索方式总是有盲区。两者互补才能覆盖更多场景。**

## RRF 为什么必要

### 直接加权求和的问题

假设有两路检索结果：

```
向量检索 Top-3:
  文档A: 余弦距离 0.92
  文档B: 余弦距离 0.88
  文档C: 余弦距离 0.85

BM25 检索 Top-3:
  文档D: BM25 分数 24.5
  文档B: BM25 分数 18.3
  文档A: BM25 分数 12.1
```

如果直接加权求和（假设各 50%）：
```
文档A: 0.92×0.5 + 12.1×0.5 = 0.46 + 6.05  = 6.51
文档B: 0.88×0.5 + 18.3×0.5 = 0.44 + 9.15  = 9.59
文档C: 0.85×0.5 + 0×0.5    = 0.425 + 0     = 0.425
文档D: 0×0.5    + 24.5×0.5 = 0 + 12.25     = 12.25
```

**问题**：BM25 分数（0~50+）天然比向量分数（0~1）大几十倍。就算设权重 `vector_weight=10, bm25_weight=0.1`，效果也不可控——因为 BM25 的分数范围和具体数据集相关，没有固定的归一化区间。

**这就是量纲问题**——就像把摄氏度和千克直接相加，权重参数没有意义。

## RRF 算法原理

### 核心思想

> **不看分数看排名。不同检索方式的分数量纲不同，但排名永远在 1~N 之间，是可比较的。**

### 公式

```
RRF_score(d) = Σ w_i / (k + rank_i(d))
```

其中：
- `d` = 某个文档片段
- `i` = 第 i 路检索（如向量路、BM25 路）
- `w_i` = 第 i 路的权重（默认 1.0）
- `k` = 平滑参数（默认 60）
- `rank_i(d)` = 文档 d 在第 i 路中的排名（从 1 开始，1 是第一名）

### 本项目实现（两路检索）

```
score(d) = w_vector / (K + rank_vector) + w_bm25 / (K + rank_bm25)
```

如果一个文档只在一路中出现，另一路的贡献为 0。

### 数值示例

取 K=60，权重相等：

```
文档A在向量排第1、BM25排第3:
  score = 1/(60+1) + 1/(60+3) = 0.01639 + 0.01587 = 0.03226

文档B在向量排第2、BM25排第1:
  score = 1/(60+2) + 1/(60+1) = 0.01613 + 0.01639 = 0.03252

文档C在向量排第3、无BM25:
  score = 1/(60+3) + 0 = 0.01587

文档D无向量、BM25排第2:
  score = 0 + 1/(60+2) = 0.01613
```

结果排序：**B > A > D > C**。两路都出现的文档天然获得更高分，只在一路出现的也不会被完全排除。

## 参数详解

### K（平滑参数）

K 控制**排名对分数的影响程度**。

```
K → 0:   1/(0+1) = 1.0  vs  1/(0+10) = 0.1  → 第10名只有第1名的 10%
         排名差异被放大，第一名有绝对优势

K → 60:  1/(60+1) = 0.0164  vs  1/(60+10) = 0.0143  → 第10名是第1名的 87%
         排名差异被平滑，前几名分数很接近

K → 120: 1/(120+1) = 0.0083  vs  1/(120+10) = 0.0077  → 几乎没区别
```

**默认 K=60** 是业界实践值（Elasticsearch 8.x 的默认值），平衡了"排名有影响"和"不会太极端"。

### weight（权重）

```
w_vector=1.0, w_bm25=0.0  → 纯语义检索
w_vector=1.0, w_bm25=0.5  → 偏向语义
w_vector=1.0, w_bm25=1.0  → 均衡（默认）
w_vector=0.5, w_bm25=1.0  → 偏向关键词
w_vector=0.0, w_bm25=1.0  → 纯关键词检索
```

权重在项目 UI 中的展示：
```
检索偏好: [纯关键词 | 偏向关键词 | 均衡 | 偏向语义 | 纯语义]
```

用 select_slider 将选项映射为 `(vector_weight, bm25_weight)` 组合。

## 完整检索管线

```
用户问题: "Python 是什么时候发布的？"
  │
  ▼
1. (可选) 查询改写
   历史: "它有哪些主要特性？" 
   改写: "Python 有哪些主要特性？"  ← 消解代词"它"
  │
  ▼
2. 向量检索 (embedder.search)
   "Python 是什么时候发布的？" → DashScope → 1024维向量
   → ChromaDB HNSW 索引 → Top 10 结果
  │
  ▼
3. BM25 检索 (bm25_index.search_bm25)
   jieba分词: ["Python", "是", "什么", "时候", "发布"]
   → BM25Okapi 打分 → Top 10 结果
  │
  ▼
4. RRF 融合 (_rrf_fuse)
   去重(按 source+page+text 唯一键) → RRF 公式 → 排序
   → Top 5 (如果启用 rerank 则取 10 个进精排)
  │
  ▼
5. (可选) LLM 精排 (reranker.rerank)
   构建评分 prompt: "文档[1] ... 文档[10] ... 请对每个文档的相关性打分(1-10)"
   → LLM 批量打分 → 按分数重排序 → Top 5
  │
  ▼
6. 返回结果
   [
     {"text": "...", "source": "python-guide.pdf", "page": 3, "score": 0.0325},
     {"text": "...", "source": "history.md", "page": 1, "score": 0.0312},
     ...
   ]
```

## 为什么 RRF 比分数归一化好

有人会问：为什么不把向量分数和 BM25 分数都归一化到 0~1，然后再加权？

| 方法 | 效果 | 问题 |
|------|------|------|
| Min-Max 归一化 | 每次检索独立归一化 | 当某路所有分都很接近时（如都在 0.85~0.92），归一化后差异被过度放大 |
| Z-Score 归一化 | 依赖均值和标准差 | 检索结果分数分布通常不是正态分布 |
| Softmax | e^s / Σe^s | 极端分数会主导排序 |
| **RRF** | 只用排名 | 简单、鲁棒、不依赖分布假设 |

RRF 的"笨"反而是它的优势——不需要对分数分布做任何假设，不需要调归一化参数，公式里只有排名和 K，**可解释性强**。

## 工业界应用

RRF 不是一个学术玩具算法，它已经在以下系统中使用：

- **Elasticsearch 8.x+**：内置 RRF 作为多路召回融合的默认方法
- **Azure Cognitive Search**：推荐 RRF 用于语义+关键词混合排序
- **Cohere Rerank**：用 RRF 融合 dense + sparse 检索结果后再做 Cross-encoder 精排

本项目的 RRF 实现和工业界做法一致。

---

## 教学小结

1. **单一检索有盲区**：向量不会精确匹配，关键词不懂语义
2. **量纲问题是核心**：向量分和 BM25 分不能直接加
3. **RRF 只看排名**：排名天然可比，绕过量纲问题
4. **K=60 是实践值**：平滑排名差异，不让第一名主导一切
5. **权重可配置**：5 种检索偏好覆盖不同场景
